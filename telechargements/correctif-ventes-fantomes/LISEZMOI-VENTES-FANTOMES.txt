LISEZMOI - VENTES FANTOMES (ecran /sales/ et caisse)
====================================================

CE QUE VOUS AVEZ SIGNALE
  - /sales/ n'affichait pas les ventes du jour ;
  - une vente encaissee au POS ne se retrouvait pas en base.

CE QUE J'AI TROUVE : LA CAUSE EST DANS LE FRONTEND, PAS DANS LA BASE
  1. lib/auth.tsx : s'il n'y avait pas de session enregistree, l'application
     se CONNECTAIT ELLE-MEME en « mode demonstration » avec le jeton
     demo_active_token_nexora. Ce jeton n'est pas un JWT : l'en-tete
     Authorization n'etait jamais envoye. Toutes les requetes partaient
     donc ANONYMES.
  2. app/login/page.tsx : si le backend ne repondait pas, le formulaire
     fabriquait un FAUX jeton JWT et un faux utilisateur, puis annoncait une
     connexion reussie. Ce faux jeton est refuse par le serveur : chaque
     ecran recevait une erreur.
  3. Depuis le correctif de securite P0, ces requetes anonymes ou a faux
     jeton sont REFUSEES (avant, elles passaient : c'etait la faille
     corrigee). Consequence : plus aucune donnee reelle n'arrivait dans les
     ecrans.
  4. Le frontend MASQUAIT ces erreurs :
       - 5 ecrans affichaient des donnees INVENTEES (placeholderData),
         dont 3 ventes fictives sur /sales/ (reference VNT-20260929-001,
         dates a 2/4/6 heures) : d'ou l'impression de « donnees pas a jour » ;
       - la caisse fabriquait un FAUX TICKET quand l'enregistrement echouait
         (le recu s'affichait, le panier se vidait, rien n'arrivait en base) ;
       - lib/api.ts simulait meme un enregistrement reussi sans backend.
  5. Le serveur, lui, est juste : la liste renvoie bien la vente du jour des
     qu'elle est enregistree (test a l'appui, voir PREUVES).
