CE QUE VOTRE DIAGNOSTIC A APPRIS (et ce que la v3 en fait)
--------------------------------------------------------------------------------
Votre PC contient DEUX copies du projet, et elles ne sont pas identiques :

  D:\NEXORA   : le POS n'y contient PAS le bilan vendeur (page sans le bouton,
                aucun fichier apps\sales\pdf_seller_report.py) -> version ancienne
  C:\NEXORA   : contient la vue PDF du vendeur (apps\sales\pdf_seller_report.py,
                deja partiellement retouchee par un autre correctif) et l'ecran
                POS avec le bouton -> c'est le projet a corriger

La v2 prenait la vue dans C:\NEXORA et l'ecran POS dans D:\NEXORA : melange de
deux copies, donc correction incomplete. La v3 corrige cela :

  * elle choisit le couple (vue PDF vendeur + ecran POS) du MEME projet ;
  * elle ecarte les dossiers qui ne contiennent pas la fonctionnalite vendeur ;
  * elle ignore ses propres sauvegardes (sauvegardes-bilan-pos-*) et les copies
    du paquet de correctif ;
  * elle affiche son choix et ses raisons AVANT de modifier quoi que ce soit ;
  * la sauvegarde est deposee dans le projet reellement modifie.

Autre robustesse ajoutee : vos helpers portent desormais des noms prefixes
(_nexora_resolve_seller, _nexora_json_error, _nexora_ventes_du_vendeur). Si votre
fichier contient deja un correctif different (c'est le cas de C:\NEXORA avec
resolve_seller), il est CONSERVE et notre version prend le dessus, sans conflit de
noms. Le script vous le dit : "correctif deja present dans ce fichier : conserve,
notre version prend le dessus".

CE QUI NE FONCTIONNAIT PAS (cause exacte, dans le code d'origine)
--------------------------------------------------------------------------------
    if seller_param and seller_user:
        sales_qs = sales_qs.filter(seller=seller_user)

Le filtre par vendeur n'etait applique QUE si les deux conditions etaient vraies.
Quand le vendeur n'etait pas identifie, le bilan etait quand meme produit : il
contenait les ventes de TOUTE l'entreprise, ou d'un autre vendeur. La
recherche du vendeur acceptait un email partiel, ignorait en silence un
identifiant invalide, et se rabattait sur « le premier utilisateur ».

Cote ecran POS, le vendeur etait saisi a la main (email) : une faute de frappe ou
un champ vide donnait un bilan errone ou complet.

--------------------------------------------------------------------------------
CE QUE FAIT LE CORRECTIF
--------------------------------------------------------------------------------
Backend
  * Vendeur identifie STRICTEMENT : identifiant UUID, email exact, nom complet,
    puis email partiel seulement s'il ne correspond qu'a un seul vendeur.
  * Vendeur demande mais introuvable : 404 clair
    {"detail": "Aucun vendeur de cette entreprise ne correspond a ..."}.
    Impossible d'obtenir le bilan d'un autre vendeur.
  * Bilan TOUJOURS limite a un seul vendeur (company + seller).
  * Seules les ventes VALIDEES (statut COMPLETED) sont comptabilisees : les
    brouillons et les ventes annulees sont exclus.
  * Un compte de role CASHIER n'obtient que son propre bilan.
  * Aucun vendeur determinable : message 400 explicite.

Ecran POS
  * Le champ email libre devient une LISTE DEROULANTE des vendeurs de
    l'entreprise (/api/v1/users/?page_size=200), vendeur connecte preselectionne,
    avec repli sur la saisie email si la liste est vide.
  * L'identifiant technique (seller_id) est envoye au serveur, y compris pour le
    lien « Ouvrir dans un onglet ».
  * Si votre modal est different, la liste n'est pas posee, mais le parametre
    seller_id est quand meme envoye : le filtre s'applique.
